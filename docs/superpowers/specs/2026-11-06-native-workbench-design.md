# Project Workbench 原生插件基础版

## 目标和授权范围

在独立的 `project-workbench` 仓库开始构建 Windows 原生项目工作平台。用户已要求开始开发，授权自行选择合理的初期技术方案。统一原生窗口承载插件提供的页面、控件、命令和设置，不嵌套独立应用窗口，不使用 WebView。首版验证平台机制；Teambition、钉钉、需求/Figma 转测试表格和电脑自动化尚不接入真实服务。

## 技术取舍（实施者决策）

- 选择 WinUI 3 + .NET 10 LTS，固定 Windows App SDK `1.8.260921001`。1.8 维护版本有成熟的 WinUI 3 接口；后续升级需重新验证原生插件兼容性。
- 相比 WPF，WinUI 更直接满足 Windows 11 / PowerToys 风格；WPF 资源加载较成熟，但此阶段不同时维护两套 UI。
- 相比声明式受限 UI，可信插件直接创建 WinUI 控件更灵活；第三方受限 UI 和独立执行进程留待后续。程序集加载上下文只能管理依赖，绝非安全沙箱。
- WinUI 主程序和插件页面使用 C# 构建控件，主程序使用标准 WinUI 资源；首版不允许外置插件 XAML/PRI 资源，避免将资源动态加载问题藏在样例中。
- 非打包（unpackaged）、x64、自包含目录分发；不裁剪、不 AOT、不单文件，保留动态程序集加载能力。编译 API 基线为 Windows 10.0.19041.0，主要支持/验收环境为仍受支持的 Windows 11（24H2 或更新版本）。API 基线不等于已验证的 Windows 10 兼容性；Windows 10 企业版/LTSC 需要另行验证。

## 首版行为

1. 原生 NavigationView 工作区，首页、插件、命令和设置入口；统一系统/浅色/深色主题。使用标准 WinUI 控件、中文说明、可访问性名称、可滚动布局和可见错误状态。
2. 与 Windows 无关的 SDK 定义插件入口、注册上下文、视图描述、异步命令和按插件分区的 JSON 设置。上下文提供 `DataDirectory`，位于所选用户根目录的 `data/<plugin-id>` 下；插件的草稿和导出使用该目录约定，冒烟模式因此不会写入真实用户目录。这是存储约定，不是文件访问沙箱。WinUI SDK 增加强类型原生视图工厂，返回 `FrameworkElement`，不把 UI 类型泄漏到 Core。
3. 插件是独立类库，主程序不引用具体插件类型。发现插件清单不执行插件代码；通过本地插件目录发现已构建插件，允许从本地目录安装新的开发插件包。
4. 清单声明 ID、名称、版本、SDK API 版本、最低主程序版本、程序集、入口类型、描述及能力说明。验证兼容性、重复 ID、目录/程序集边界和错误清单；单包失败不阻断其他包。
5. 初次加载需由用户显式启用并确认信任。状态保存在用户目录；启用失败撤销注册；停用取消生命周期令牌、调用停止并撤销视图/命令/设置。关闭所有相关页面引用。停用不声称卸载程序集；更新/移除要求退出程序后操作并重启。
6. 自定义非 collectible AssemblyLoadContext 和 AssemblyDependencyResolver 解析托管依赖，共享平台 SDK、WinUI 和系统框架类型，避免同名契约类型不匹配。可信插件同进程执行，不能保证崩溃、死循环或恶意行为隔离。
7. 两个独立示例插件：工作摘要（演示数据，本地草稿）和测试用例（演示数据，本地表格与导出）。各提供原生页面、命令和持久设置，均明确标记演示。不采集真实数据，不执行电脑自动化，不调用 AI/第三方 API。
8. 安装只复制本地开发包到用户插件目录、验证内容，不执行包代码。拒绝路径穿越、符号链接、同 ID 重复包、缺失入口文件；首版不覆盖现有/已加载包，不提供签名验证或在线市场。

## 结构

- `src/Workbench.Sdk`：跨平台契约。
- `src/Workbench.Core`：发现、校验、安装、设置、注册表、加载和生命周期。
- `src/Workbench.WinUI.Sdk`：原生视图工厂契约。
- `src/Workbench.App`：窗口、原生导航、插件管理、命令和设置页面。
- `plugins/Workbench.*.Sample`：两个独立演示插件；构建时作为插件包复制，不静态链接主程序。
- `tests/Workbench.Core.Tests` 与 `tests/Workbench.TestPlugin`：真实磁盘/程序集测试夹具和运行时测试。
- `scripts`：PowerShell 构建/发布；`.github/workflows`：跨平台 Core 测试与 Windows 原生构建。

## 验收和边界

Linux 可运行真实 Core 测试（包括动态加载独立 DLL、启停、重启后的设置、注册回滚、命令执行、错误依赖与包边界）。Windows CI 应编译和发布真实 WinUI 主程序及两个插件，并上传完整自包含目录。增加独立临时用户目录下的 `--smoke-test` 模式，仅加载随构建分发的两个已知示例包，在真实 WinUI UI 线程创建原生页面/设置、执行本地命令、验证停用和关闭，输出机器可读结果并用进程退出码反馈。该模式不扫描用户安装包、不读取真实用户设置；若托管 CI 无交互桌面而无法运行，必须明确报告，不能静默跳过。

C# 跨目标编译、Windows CI 构建、Windows 原生自动冒烟和人工界面验收是不同证据，分别记录。当前 Linux 环境无法证明真实窗口、主题、高 DPI、辅助功能、文件选择器或原生关闭流程工作正常；必须在 Windows 实机补验，不生成假截图、不宣称已完成 UI 验收。
